## What this batch is, and what it is not

Thirteen items were triaged: **seven fixes**, **six sanctions**. A sanction here is not a dismissal — it is
a recorded ruling that the behaviour is correct, with the reason the next person will need. Three of the
sanctions carry a documentation change, because the cost the register measured was *discoverability*, not
behaviour: each was "a grammar fact learnable only by triggering it", and each fired at dispatch, the one
moment with a 180-second window against it.

Two triage errors were caught by an independent review before this document existed, and both are recorded
here rather than quietly corrected — they are the reason the review happened:

- **I-24(d) was triaged FIX and is SANCTION.** The claim was a silent no-op. Measured: the parser refuses
  with a named message that lists every declared flag (`cli.py:331-336`), and `--slot`'s own help already
  reads *"the workspace directory; its basename becomes the slot name"*. The register's "silent in the
  sense that it exits without doing anything a casual reader would notice" is a misreading of a legible
  refusal.
- **I-27's proposed fix would have destroyed the verb.** See I-27 below. It is the most important entry in
  this document.

A third correction: the premise that `fleet close` already carries a liveness protection that `apply`
lacks is **false**. `_do_close` refuses via `_pane_refusal`, which reads pane-guard's `10`/`11` only; a
live-but-idle pane closes without complaint. The asymmetry argument for I-10 does not hold, and I-10's fix
is justified on its own terms instead.

## The fixes

### F1 · I-16 — `pane-guard` reads a selection dialog as an idle pane

**The defect.** `_do_pane_guard` (`cli.py:3798-3865`) branches: not-alive → `13`, capture-failed → `14`,
not-claude → `12`, `busy()` → `11`, `unsubmitted()` → `10`, else `0 safe`. A pane showing an
`AskUserQuestion` selection dialog — *"Enter to select · Tab/Arrow keys to navigate · Esc to cancel"* —
satisfies none of the first five and lands on `0`, whose detail reads *"a quiet claude pane with an empty
input box"*. That is the same answer an idle worker gets, and for a coordinator the two are opposites:
idle means *nothing needed*; blocked at a question means *you are the blocker*. A coordinator polling on a
schedule sees a healthy quiet pane indefinitely.

**The fix.** A distinct code and verdict for *displaying a selection dialog, nothing queued*, detected from
the dialog's banner the way `_BUSY_MARKERS` and `_STATUS_LINE_MARKERS` already detect other banners
(`session.py:182-206`). The banner text is quoted verbatim in the register, so the fixture is derivable
from evidence rather than invented.

**What it must not regress.** `SI-37` (`session.py:167-183`) deliberately removed `"esc to cancel"` from
`_BUSY_MARKERS`, because that string is what a *modal* offers while it waits for a human, and matching it
as `busy` reported `11 mid-turn` for a session that had not started and never would. This fix does **not**
restore that string to `_BUSY_MARKERS` and cannot resurrect that false positive: it adds a third answer
rather than re-widening the first. `SI-37`'s comment argues the removal "costs nothing, because
`unsubmitted` ALREADY detects the modal's selected line as text in the input position" — that is true for
modals whose selected row renders a caret in `_CARET` (`session.py:54`), and **measured false for the
AskUserQuestion dialog**, which is this defect. **The comment becomes partially false when this lands and
must be amended in the same change**, with the measurement that makes it false.

**Blast radius — larger than the code.** Adding a pane-guard code touches:
- `PANE_GUARD_CODES` and the `EXIT_CODES_ALL` registry (`cli.py:172-210`) — *"a verb returning a code
  absent from here fails the suite"*;
- the derived `_codes_block()` usage;
- **prose contracts in shipped skills**, which are the real consumers: `skills/using-fleet/SKILL.md:166`
  polls with exact equality (`[ $? = 10 ]`), and `coordinating-instants/SKILL.md:57` and
  `harvesting-an-instant/SKILL.md:59-65` document the code set.

`bin/fleet-view` and `scripts/claude-watchdog.sh` were assumed to be consumers and are **not** — neither
mentions pane-guard at all. Do not touch them for this.

Per `fleet/CLAUDE.md`, changing a verb a skill names requires a **§P re-run**.

### F2 · I-9 / I-18 / I-24(second) — registration writes a relative `issues_path`

**The defect.** `Harvest.record_dispatch` (`harvest.py:408`) registers the watched source as
`Path(rec.base_instant) / REGISTER_NAME`. `rec.base_instant` is a bare 8-digit id, not a path, so the
stored `issues_path` is `09101704/ISSUES.md` — relative to nothing. The harvest tick resolves it against a
different directory, reports `unreadable-source`, and **the base instant's register contributes nothing to
every tick from then on**. Compare `_do_init` (`cli.py:1013`), which passes an absolute path and is
correct.

Seven recurrences are recorded. Three properties make it worse than a one-off:

1. **It is not dispatch-specific.** `record_dispatch` is reached from `cli.py:1490` (dispatch) **and
   `cli.py:1636` (resume)**. Scope the fix as *registration*, not as *dispatch*.
2. **Any dispatch re-breaks an already-repaired row.** A hand-repair is never durable.
3. **The failure is an absence.** A broken row reports nothing, which is indistinguishable from a register
   with nothing to say — the blind-zero shape this codebase has been bitten by repeatedly.

**The fix.** Resolve the base id to its real instant directory at registration time. `Harvest` itself knows
only the store (`harvest.py:305`), but `rec.child_instant` is absolute (`cli.py:1425`, `cli.py:1621`), so
`Path(rec.child_instant).parent` **is** the instants directory. Scan it for the folder whose `curr` field
equals `rec.base_instant`.

**Three constraints, each of which fails the change if missed:**

- **`identity.resolve` cannot be reused as-is.** It requires the recorded name to parse as a full
  `InstantName` and its parent to be a real directory (`identity.py:93`); a bare id yields
  `parent == Path('.')`.
- **An ambiguous base must refuse, not guess.** An `-abort-` and an `-inflight-` folder for one id sort
  together; this is what `AmbiguousId` exists for.
- **`ROOT_BASE` (`00000000`) must fall through to today's behaviour.** It is synthetic and resolves to no
  directory; `unharvestable()` exempts it (`harvest.py:~590`) and `it/RESULTS.tsv:223` (`A5f`) is PASS on
  exactly that path. Break it and A5f flips red.

**The second half, now observed.** I-18 predicted that *"an absolute path to a renamed instant folder is
equally silent"*; I-24(second) records it happening — harvesting `m7.3` renamed its folder
`-inflight-` → `-complete-`, and a correctly-absolute row silently stopped resolving. **The harvest's own
success is what breaks it.** `register_path` (`harvest.py:448`) carries rename-tolerant resolution; the
implementation must determine why it did not save this case and close both halves, or state which half
remains open and why. A fix that closes registration and leaves renames silent has fixed the half that was
already being worked around.

### F3 · I-24(c) — an invented placeholder is refused only at real dispatch

**The defect.** A charter written with a plausible-but-undeclared placeholder (`{{LINEAGE_BASE_SHA}}`)
fails with `BadInput: unresolved placeholder(s)` (`profiles.py:171`) — correctly, but **only on the real
dispatch**, costing a full rollback plus the verification that the rollback was complete. `_do_dispatch`'s
dry-run block (`cli.py:1369-1383`) returns before `InstantName.new` (`cli.py:1386`) and before
`profile.render`, so `--dry-run` — the verb whose entire purpose is to answer this cheaply — cannot see it.

**The fix.** Validate placeholders inside the dry-run path. `Profile.render` (`profiles.py:157-176`)
substitutes by key and raises on leftovers, so **detection depends on the key set only, never on the
values**: a dry run can pass `SLOT: "(dry-run)"` and validate honestly without claiming a lease. Check
whether `profiles.lint()` (`profiles.py:190`), which currently has no CLI caller, is the right vehicle
rather than a second validator.

### F4 · I-27 — `fleet abort` leaves a zombie when the slot release refuses

**The defect.** `_do_abort` (`cli.py:2563`) runs: write reason → `sessions.kill(record.tmux)` →
`pool.release(record.slot)` → `child.rename(target)`. `pool.release` can refuse when a live pid holds the
slot as its cwd (`OBS-48`). By then **the session is already dead**, and the board reads `UNREACHABLE` plus
a spurious `UNKNOWN-SESSION` row for the orphan pid: session gone, folder not renamed, slot not released,
milestone not disowned. The documented contract — *"rename it `-abort-` WITH A RECORDED REASON"* — did not
hold.

**The fix that was proposed and must NOT be built.** Moving `pool.release` before `sessions.kill` looks
like the obvious correction and **destroys the verb**. A dispatched worker's cwd *is* its leased slot
(`fleet/CLAUDE.md`, "Known gaps"), so at that point the worker is guaranteed live in that cwd, the release
is guaranteed to refuse, and **no live worker would ever be abortable again**. This is recorded because it
is the kind of fix that reviews well and fails in production.

**A second correction.** The docstring (`cli.py:2571-2575`) is not self-contradictory, as first claimed: it
names the *rename* as the irreversible step, and the fallible steps do precede it. The real defect is that
`sessions.kill` is **also** irreversible and the docstring does not count it. That is a reasoning gap in
the documented invariant, and the docstring must be corrected alongside the behaviour.

**What to build instead.** The register's own recovery — *"wait for the pid, then re-run"* — already works,
because `kill` is a no-op on a dead session and the re-run completed every remaining step. The fix makes
that recovery reachable without reading a register:

1. a **bounded wait** between `kill` and `release` for the slot's cwd-holding pids to exit, which converts
   the common case into a complete abort;
2. when it still refuses, a refusal that **states the partial state explicitly** — session closed, slot
   still leased, folder still `-inflight-`, milestone still claimed — and names re-running the identical
   command as the completion, so `UNREACHABLE` + `UNKNOWN-SESSION` stops reading like corruption.

**Do not** complete the rename on the refusing path: a folder already renamed `-abort-` makes the
documented re-run refuse, which would remove the one recovery that works today.

`tests/test_cli.py:1761` pins the transaction and must keep passing; `it/run-O.sh` has no abort-ordering
injection case, so this needs one.

**⚠️ Ruled OPEN, not delivered in this batch (2026-09-13).** The `it/run-O.sh` case was not written. No
implementer in this batch was permitted to run the integration harness — a run rewrites tracked registers
and dirties the tree, which refuses the release cut — so building it would have meant committing
failure-injection shell that nothing had executed, with the release gate as its first run. That is how a
gate fails for a reason unrelated to the change, and the task's own implementer declined it on the same
grounds. **The consequence is carried, not hidden:** the abort partial-state path has hermetic coverage
only, and the hermetic tier structurally cannot prove anything about a real pid holding a real cwd, which
is the entire mechanism `OBS-48` refuses on. Whoever next runs §O owns writing it.

### F5 · I-10 — `apply` says nothing about a still-live worker

**The defect.** A terminal status was applied to a milestone whose worker session was still being iterated.
Every signal read finished — the folder was `-complete-`, the board `COMPLETE`, the review `READY`, the
proposal note said *"done"* — and all four were wrong. `fleet apply` has **no inverse**, and
`fleet milestone` refuses to amend an existing row, so the revert was a hand edit of `roadmap.json`.

**The fix.** `_do_apply` (`cli.py:2384`) emits an explicit warning row when the instant's tmux session is
still alive. `_record_for` already resolves path → record by stable key, so the plumbing exists.

**A warning, not a refusal**, and the reason is recorded: a legitimately finished worker may keep its pane
open, and a hard refusal would block correct close-outs. **State honestly in the implementation that this
warning rests on the same liveness signal whose unreliability is F6's subject** — it raises the floor; it
does not make the signal trustworthy.

### F6 · I-21 / I-26(second) — `pane-guard` reported an empty box for a box holding text

**The defect, and why it outranks F1.** Three consecutive `pane-guard` samples returned `0` with
`queued_text` empty for a pane whose input box visibly held `ratify D-7, I-11 and I-30 so this can close`.
The "take three samples" defence is designed against a *flaky* observer and does nothing against a
*consistently wrong* one. `fleet close --dry-run` returned `would-close true`, because `_pane_refusal`
reads the same signal — **the safeguard and the check it backstops share one point of failure.** It
recurred on `m2`, and that time the text named real outstanding work (a temporary CI carve-out that ships
into a merged lineage if nobody removes it). Both times the only thing that caught it was capturing the
pane by hand.

**Why the root cause is NOT fixed in this batch.** No raw capture survives. Both
`UNSUBMITTED-PANE-TEXT-AT-CLOSE.md` artifacts preserve the *text*, not the rendered rows — so what
`_caret_content` actually saw is unknown. `unsubmitted` and `_caret_content` are dense with recorded
regressions in both directions (`FI-24`'s last-caret rule, `N4`'s echo trap, `FI-208`'s attribute
handling, `_undim`'s dim-cell rule), and a change made against a guess would be as likely to re-open one
of those as to close this. **Speculating a fix here would be the fabrication this codebase exists to
refuse.**

**What is built instead — the thing that makes the next occurrence solvable.** `pane-guard` gains the
ability to preserve the raw capture that produced its verdict, so a third occurrence arrives with an
artifact instead of another anecdote. The known defect is recorded in the shipped skills with the standing
rule both incidents actually turned on: **capture the pane before any teardown; `pane-guard` is usable for
"is it safe to type" and is not evidence that a pane holds nothing.**

### F7 · I-25 — a first harvest tick reports a population as a delta

**The defect.** The first tick against a source returned `36 new: I-1 … I-36` — the entire register —
because the diff had no prior state. The tool emits a `no-prior-state` row saying so, but `N new` is the
shape of a *result*, and a routine tick read as "36 things just happened" is the mirror of the blind-zero
failure: the observer's state mistaken for the subject's.

**The fix.** Wording and row order in `harvest.run()` only — a first-tick count reads as a population and
says so, before the headline rather than beside it. No behaviour change.

## The sanctions

### S1 · I-1 — `fleet init` is not idempotent

**Ruling: correct as built.** Instant names embed a minute-resolution timestamp, so two runs a minute apart
are two legal, different instants — there is nothing to collide with. A same-minute re-run *is* refused
(`cli.py:1010`, `target.exists()`). The register's own root cause says this; the apparent failure was the
operator's trailing shell glob.

**Documentation, one line:** `init` also registers a watched source (`cli.py:1013`), so deleting a stray
instant folder by hand leaves a dangling registry row. Deleting the folder is half the cleanup.

### S2 · I-3 — dispatch renders the seed but does not deliver it

**Ruling: by design, already documented** in `fleet/CLAUDE.md` under "Known gaps". The mechanism performed
correctly throughout: `seed-check` reported `not-delivered`/`unverifiable`, and moved to `attested` once
delivery was attested. `attested` being weaker than `verified` is the design being honest about its own
evidence, not a defect. No change.

### S3 · I-24(a) — a retired milestone id is never reissued

**Ruling: correct, and load-bearing.** Id permanence is the rule everywhere in this codebase — `OBS-14`,
append-only registers, instants that may hold only one state. Reissuing `m8` would make every prior
reference to `m8` ambiguous, and the register itself is full of cross-references that depend on ids meaning
one thing forever. The cost — roadmap ids drifting from whatever numbering you had in mind — is the correct
trade.

**Documentation:** `--retire` states in its own output that the id is retired permanently and the next add
takes a new one, so the drift is expected rather than discovered later.

### S4 · I-24(b) — `--base` takes an id where `--from`/`--profile`/`--instant` take paths

**Ruling: correct, and the inconsistency is the point.** A base is a *stable key*; an instant's folder is
renamed on every state transition, so a path stored as a base would go stale the moment the base instant
finished. F2's entire second half is what happens when a path goes stale. `InstantName.__post_init__`
(`identity.py:40`) already names the rule on failure.

**Documentation:** `--base`'s help text says outright that it is a bare 8-digit id and not a path, and names
the reason. The error gains a hint when the value it rejected looks like a path.

### S5 · I-24(d) — `enroll --slot <name> --path <dir>` "prints usage and enrols nothing"

**Ruling: measured, and the premise is wrong.** Run directly, it prints:

> `enroll: '--path' is not a flag enroll declares. Declared: --dry-run, --help, --home, --instants-dir,
> --porcelain, --root, --slot. Refused, not ignored: a parser that accepts what no spec declares is a
> second, hand-maintained copy of the flag list.`

then the derived usage, in which `--slot` reads *"(required) the workspace directory; its basename becomes
the slot name"*. That is a named refusal that lists the declared flags and documents the correct form —
not a silent no-op. No change.

### S6 · I-26(first) — the auto-mode classifier blocks pane delivery on message content

**Ruling: outside this codebase.** The refusals (`[Production Deploy]`, `[Create Public Surface]`) come
from the harness's own auto-mode classifier, which keyed on the message's subject matter — it discussed
authorising a tag push — rather than on what the command did. A `cp` of a local file was refused as a
production deploy. No fleet change can address this, and the coordinator was right not to paraphrase until
it passed: *"the whole point of a guard is that you do not get to talk your way past it."*

**Documentation:** the workaround is promoted from an incident note into the shipped coordinator guidance —
**keep a coordinator→worker pane note to a pointer ("read FILE-X, the operator answered") and put the
substance in a file.** The pointer carries no deploy-shaped vocabulary and passes.

## Register hygiene (raised, not fixed here)

The source register contains **duplicate ids**: `I-24`, `I-25` and `I-26` each appear twice (lines 504/665,
534/690, 558/717). In an append-only register whose whole value is that an id names one thing, that is a
defect in its own right, and it hid two entries during the first triage pass — including the one that
confirmed F2 applies to `resume`. This belongs to the register's owner, not to this batch; it is recorded
here so the next reader of either entry knows the other exists.
